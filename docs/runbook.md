# 장애 대응 절차 (Runbook)

## 증상별 대응

### 1. 대시보드에 "감시가 중단된 것으로 보입니다"

하트비트가 25분 이상 끊긴 상태다 (`checkHeartbeat`).

1. 워커 프로세스가 살아 있는지 확인
2. 워커 로그에서 마지막 틱의 예외 확인
3. 워커를 재시작한다 — 상태는 DB에 있으므로 감시 조건은 보존된다
4. 재시작 후에도 하트비트가 안 올라오면 DB 연결을 확인

**중요**: 이 경고가 뜬 동안 놓친 취소표는 복구할 수 없다. 원인 규명보다 재기동이 우선이다.

### 2. `CONTRACT_BROKEN` — 사이트가 바뀌었다

응답이 `docs/site-contract.md`의 스키마와 다르다. **자동 복귀하지 않는다.**

1. `/contract-check`를 실행해 무엇이 어떻게 달라졌는지 표로 확인
2. 파싱만 바뀐 것인지, **예약 절차 자체가 바뀐 것인지** 판단한다
   — 후자라면 `/recon`을 처음부터 다시 돌린다
3. `docs/site-contract.md`를 갱신하고 `src/adapters/audeum/contract.ts`를 고친다
4. 새 응답을 픽스처로 추가한다 (`tests/fixtures/`)
5. `pnpm verify` 후 배포, 그리고 감시를 수동으로 재개한다

**하지 말 것**: 파싱 에러를 try/catch로 삼켜 "여석 없음"으로 처리하는 것.
그러면 시스템이 조용히 영원히 실패한다.

### 3. `CIRCUIT_OPEN` — 연속 5회 실패

30분 뒤 자동으로 재개된다. 그 전에 확인할 것:

- 사이트가 내려갔는가? (브라우저로 직접 접속)
- 429/503을 받고 있는가? → 폴링 주기를 늘린다
- 우리가 차단됐는가? → **즉시 중단하고 사용자에게 보고.** 우회하지 않는다

### 4. `FAILED_NEEDS_HUMAN` — 감지했으나 예약 실패

재시도 2회를 소진했다. 감시는 계속되므로 다음 취소표를 노린다.

1. `runs/<timestamp>/`의 스크린샷과 페이로드로 실패 지점을 특정
2. 흔한 원인:
   - **그 사이 남이 채감** (`SLOT_TAKEN`) → 정상. 코드 문제 아님
   - **CAPTCHA/본인인증** (`NEEDS_HUMAN`) → 자동화 대상이 아니다. 사용자에게 링크 전달
   - **폼 필드 변경** → 계약 드리프트. 위 2번 절차

### 5. 예약은 됐는데 QR 티켓 메일이 안 온다

오디움 측 발송 지연일 수 있다 (5분 내 발송이 정상). 10분 이상 지나면:

1. 대시보드의 예약 확정 기록(`confirmationId`)을 확인
2. 오디움에 직접 문의 (02-574-5175)
3. **중복 예약을 시도하지 않는다** — 1인 1매이고 중복은 취소 사유다

### 6. 가지 못하게 됐다

**즉시 취소한다.** 예약 확인 메일의 취소 링크를 사용한다.
사전 통보 없는 불참은 향후 예약 제한 사유다.

## 정기 점검

- `/contract-check` — 주 1회 (사이트 개편 조기 발견)
- 하트비트 연속성 — 대시보드에서 상시 확인
- `runs/` 디렉터리 용량 — 개인정보가 섞여 있으므로 주기적으로 정리
