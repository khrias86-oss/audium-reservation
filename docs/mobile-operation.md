# 모바일 전용 운영 설계

## 점검에서 드러난 가장 큰 문제

현재 배포 계획(`deploy/cloudrun.md`)은 **`gcloud` CLI 명령 실행을 전제**한다.
서비스 배포, 잡 생성, 시크릿 등록, 스케줄러 설정이 전부 터미널 명령이다.

**모바일에는 터미널이 없다.** 즉 지금 설계대로는 M7(배포)에 영원히 도달할 수 없다.
코드가 아무리 잘 돌아도 사용자가 켤 수 없으면 완성이 아니다.

이건 코드 결함이 아니라 **설계가 사용자의 실제 환경을 반영하지 못한 문제**다.

## 해결: GitHub 자체를 운영 플랫폼으로 쓴다

GitHub 모바일 앱과 모바일 웹은 이미 필요한 조작 수단을 전부 제공한다.

| 필요한 일 | 모바일에서 하는 방법 | 새 계정 |
|---|---|---|
| 감시 조건 설정·변경 | 저장소의 `watches.json` 파일 편집 | 불필요 |
| 즉시 실행 | Actions 탭의 **Run workflow** 버튼 | 불필요 |
| 현재 상태 확인 | Actions 실행 이력 + 잡 서머리 | 불필요 |
| **빈자리 알림 수신** | **GitHub Issue 생성 → 이메일 + 앱 푸시** | 불필요 |
| 예약자 정보 보관 | Settings → Secrets | 불필요 |
| 전체 중지 | 워크플로 Disable 토글 | 불필요 |

### 알림 설계가 특히 중요하다

원래 계획은 Resend나 Gmail SMTP였고, 둘 다 별도 계정과 API 키 발급이 필요했다.
모바일에서 하기 번거롭고, 키 관리 부담도 생긴다.

대신 **빈자리를 감지하면 GitHub Issue를 연다.** GitHub는 저장소 Watch 중인
사용자에게 이슈 생성 시 이메일과 모바일 앱 푸시를 자동으로 보낸다.

- 설정할 것이 없다 (이미 저장소 소유자이므로 기본 알림 대상)
- 이슈 제목에 날짜·회차를 넣으면 **알림 제목만 봐도 결과를 안다**
- 이슈 본문에 예약 페이지 직링크를 넣으면 **탭 한 번으로 이동**
- **이슈의 존재 자체가 중복 알림 방지 상태**가 된다 — 같은 슬롯에 대해
  열린 이슈가 있으면 다시 알리지 않는다. 별도 상태 저장소가 필요 없다

이건 우회책이 아니라 이 상황에서 객관적으로 더 단순한 설계다.

## Actions 실행 시간 예산 (반드시 확인할 제약)

private 저장소의 무료 Actions 실행 시간은 **월 2,000분**이고, 실행 1회는
**최소 1분으로 반올림 과금**된다.

| 폴링 방식 | 월 실행 횟수 | 소요 분 | 판정 |
|---|---|---|---|
| 10분 간격 24시간 상시 | 4,320회 | 4,320분+ | ❌ 한도 초과 |
| 10분 간격, 07~23시(KST)만 | 2,880회 | 2,880분+ | ❌ 초과 |
| **감시 활성 + 관람 7일 이내 + 07~23시** | 감시 1건당 약 672회 | 약 672분 | ✅ 월 2~3건 가능 |
| 저장소를 public으로 전환 | 무제한 | 무제한 | ✅ 단, 코드 공개 |

**채택: 조건부 폴링.** 감시 대상이 없거나 관람일이 멀면 워크플로가 즉시 종료한다
(수 초 소요, 1분 과금). 실제 폴링은 의미 있는 구간에서만 돈다.

오디움은 목·금·토만 운영하고 취소표는 관람 1~2일 전과 당일 오전에 몰리므로,
이 방식은 예산을 아끼는 동시에 **잡을 확률이 높은 구간에 자원을 집중**한다.

### 감수해야 할 단점

GitHub Actions의 `schedule`은 **최소 5분 간격이고 혼잡 시 10~30분 지연**될 수 있다.
"정확히 10분마다"는 보장되지 않는다.

취소표는 보통 수 분~수 시간 열려 있으므로 치명적이지는 않지만, 오픈 직후
초 단위 경쟁에는 부적합하다. 정확한 주기가 꼭 필요해지면 Cloud Run으로
옮긴다 — 런타임이 플랫폼 중립이라 `Dockerfile`을 옮기면 되고, 그때는
PC를 쓸 수 있는 상황일 것이다.

## 상태 저장

외부 DB(Neon 등) 없이 간다.

| 상태 | 저장 위치 | 이유 |
|---|---|---|
| 감시 조건 | `watches.json` (저장소) | 모바일에서 직접 편집 가능 |
| 중복 알림 방지 | **열린 이슈의 존재 여부** | 별도 저장소 불필요 |
| 예약 멱등성 키 | 이슈 라벨 + 닫힌 이슈 이력 | 같은 슬롯 재예약 차단 |
| 직전 스냅샷 | Actions 캐시 | 유실돼도 첫 틱처럼 동작할 뿐 |
| 하트비트 | 마지막 워크플로 실행 시각 | Actions가 이미 기록 중 |

`src/store/types.ts`의 `Store` 포트는 그대로 두고 GitHub 기반 구현을 추가한다.
core 로직은 한 줄도 바뀌지 않는다 — 포트를 나눠둔 설계가 여기서 값을 한다.

## 이 설계로 바뀌지 않는 것

- `src/core/`의 모든 가드레일 (5분 하한, 정확 일치 예약, 1인 1매, DRY_RUN 게이트)
- 계약 미확정 시 실행 차단 (`assertContractReady`)
- 파싱 실패를 여석 없음과 구분하는 `CONTRACT_BROKEN` 상태
- 준수 요건 — robots.txt 확인, 봇 탐지 회피 금지, CAPTCHA는 사람에게 이관

플랫폼만 바뀌고 안전장치는 전부 유지된다.

## Cloud Run 경로는 폐기하지 않는다

`deploy/README.md`의 무료 한도 계산과 `deploy/budget-safety.md`의 예산
안전장치는 여전히 유효하다. PC를 쓸 수 있게 되면 그쪽이 더 정확한 주기를 준다.

**GitHub 경로 = 지금 당장 모바일로 돌릴 수 있는 것**
**Cloud Run 경로 = 나중에 더 정확하게 돌릴 것**

둘 다 같은 `src/`를 쓴다.
